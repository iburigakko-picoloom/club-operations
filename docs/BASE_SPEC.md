# 部活運営アプリ — 実装仕様書 v1.0

作成日：2026-09-05  
用途：GPT-5.6 Luna / Astra / Codex 等への実装引き継ぎ  
対象：大学バドミントン部の幹部・運営担当者が使う共有PWA

## v0.9の優先追補（2026-09-06）

最新要望によりLINEログインの基盤・アカウント・グループ選択・明確な招待導線を追加した。LINEメッセージ送信は対象外のまま。実LINE接続・秘密設定・公開はCodex側で行う。

配車は常時表示の「往復同じ／行き・帰り別」、明示的な統合元選択、コピー元と今回の表を区別した確認、画像プレビュー→保存／共有を正本とする。配車のコピーでは対象日の単価・利用日・通知設定を維持する。配車不要指定・個別精算調整はリセットする旨を確認画面で示す。予定画像は毎回部活のみを既定とし、幹部込みは明示選択。幹部予定と締切の重ね表示は変更しない。

本ZIPで実際に含むファイル名は `docs/BASE_SPEC.md`、`docs/UI_SPEC.md`、`club-demo.html`、`web/`、`server/`。古い引き継ぎパックのファイル名を推測して新規に探さない。新しい仕様詳細・実装状態・未検証項目は `docs/CODEX_HANDOFF_v0.9.md` と `QA_REPORT.md` を優先する。

## 0. この文書の読み方・優先順位

これはアイデア募集ではなく、会話で固めた仕様を実装するための文書である。アプリ全体を勝手に再設計しない。

優先順位は、**ユーザーの最新の明示要望 → 本書の確定仕様 → UI_SPEC → HTML参照 → 過去の生成画像**。生成画像中の誤字、人数の不整合、架空の属性、不要なラベルを仕様として採用しない。既存予定・練習メニューの実装については、実ファイルを確認できた範囲だけを「既存」と呼ぶ。

「確定」はユーザーが指定したもの。「補完判断」は実装可能にするための推奨初期値で、ユーザーが明言した事実ではない。補完判断は末尾に一覧化する。未入手の既存ソース以外を理由に実装全体を止めず、独立した箇所は進める。ただし未実装を完成扱いしない。

### 最重要変更

- 配車で最初にドライバーだけを選ぶ画面は**廃止**。
- 配車編集の左約2/3が車、右約1/3が部員一覧。両方向・車同士をドラッグできる。
- 配車表の追加時に、既存の部活予定から対象日程を選ぶ。予定があるだけで配車を自動作成しない。
- 過去の配車の配置をコピーできる。
- 配車が必要なのに未配置の人は赤で表示する。
- 共有用配車表は、**運転者名を列見出し、その下に同乗者**。**「1台目」「2台目」は表示しない。**
- ホームは「お知らせ」「自分のやること」だけ。
- 会計・体育館料金・お知らせ既読管理は初期版から除外。

## 1. 目的・利用者・スコープ

### 1.1 目的

予定、担当者、出欠、配車、練習メニュー、備品を一つのアプリにまとめる。役割ごとの業務に直接入れ、同じ情報を何度も入力しない。一般部員全員にアプリ導入や出欠回答を要求する設計ではない。

### 1.2 二種類の「人」

1. **部員名簿**：配車・出欠・参加者表示の対象となる全部員。ログイン不要。
2. **運営メンバー**：グループへ招待され、ログインして操作する人。主に幹部。名簿の本人に任意で紐づく。

この二つを混ぜない。「幹部上／幹部以下」は学年による活動区分であり、ログイン権限や運営担当権限とは別物。幹部以下の全員がアプリ編集者になるわけではない。

### 1.3 初期版に含むもの

グループ、運営メンバー招待、担当・権限、ホーム、お知らせ、部活予定、幹部予定、やること、PWA通知、部員名簿、出欠、配車、配車履歴、月次配車精算、体育館、既存練習メニューの統合、軽量な備品管理。

### 1.4 初期版に含めないもの

一般会計、収支帳簿、部費集金、体育館料金計算、在庫入出庫台帳、自動発注、チャット、投票、LINEでのメッセージ送信・友だち一覧・LINEグループ同期、一般部員用ログイン導線、既読管理、ホームの自由な並べ替え、AIによる配車最適化、免許証・車検証などの登録。

除外した機能の大きな空カードや「近日公開」をホーム・運営に残さない。配車精算は会計の延期とは独立して実装する。

## 2. 情報構造・ナビゲーション

下部タブは順番も含めて固定。

**ホーム｜予定｜やること｜運営｜設定**

- 運営：出欠、配車、体育館、練習メニュー、備品。
- 設定：グループ、部員、運営メンバー、担当・権限、通知、配車設定。
- 体育館の管理本体は運営に一本化。設定から入口を置く場合も同じ画面へのリンクとし、別データにしない。
- 配車は運営の子画面。下部タブ「運営」を「配車」に置き換えない。
- 作成・詳細画面を開いても、元の下部タブの選択は維持する。編集専用全画面では下部タブを一時非表示にしてよい。
- 長い説明文を常設しない。未入力エラー・通信エラー・取り消しなど、その場で必要な情報だけを短く表示する。

## 3. グループ・オーナー

### 3.1 グループ

すべての共有データは一つの `group_id` に属する。グループAの予定にグループBの部員を割り当てられないことを、画面だけでなくサーバーでも検証する。

現在のグループ名をホームの上部と設定の上部に表示する。複数所属時はグループ名タップで切り替え。v0.9ではログイン後に1グループでも選択画面を表示し、アカウント設定や招待参加へ進める。切り替えたら、そのグループのホームに戻し、選択途中の他グループの部員・通知対象を持ち越さない。

### 3.2 作成・参加

LINEまたは移行用メールログイン → グループを選ぶ（作成／招待参加も可能） → グループ作成者がオーナー。招待はオーナーだけが発行できる。推奨初期設定は有効期限付き・失効可能な招待リンク。一般部員を名簿へ追加しただけでは招待や通知を送らない。

### 3.3 オーナー

担当者、運営メンバー、グループ設定を変更可能。一つの担当に複数人、1人に複数担当を指定可能。年度交代時にオーナー移譲・担当差し替えができる。唯一のオーナーの退出は移譲後に行う。名簿削除で配車履歴・精算履歴を消さない。

## 4. 権限テンプレート

詳細設定を毎回要求しない。標準は「運営メンバーは閲覧、担当者はその機能の編集、オーナーは全操作」。閲覧と編集は別権限として実装する。

| 機能 | 一般の運営メンバー | 機能担当者 | オーナー |
|---|---|---|---|
| 部活・幹部予定 | 閲覧 | 予定の作成・編集・中止 | 全操作 |
| やること | 閲覧、自分の担当タスク完了 | 作成・割当・編集 | 全操作 |
| お知らせ | 自分が対象の投稿を閲覧 | 投稿・編集 | 全操作 |
| 出欠 | 閲覧 | 変更 | 全操作 |
| 配車・履歴・精算 | 閲覧 | 作成・編集・月次確定 | 全操作 |
| 体育館 | 閲覧 | 登録・編集 | 全操作 |
| 練習メニュー | 閲覧 | 既存機能による編集 | 全操作 |
| 備品 | 閲覧 | 数量・項目変更 | 全操作 |
| 部員名簿 | 閲覧 | 部員担当が編集 | 全操作 |
| 担当・権限・招待 | 自分の権限を確認 | 原則変更不可 | 全操作 |

補完判断：やること担当は「運営管理担当」としてオーナーが指定。タスク作成者も自分が作成したタスクを編集できるが、権限を外された後は不可。お知らせの対象制限はアクセス制御でも守る。権限のない編集ボタンを単にグレーに大量表示せず隠す。ただし閲覧可能な運営メニューは隠さない。

## 5. ホーム

上部はグループ名。その下は**お知らせ、自分のやることの二つだけ**。

- お知らせ：最近の対象投稿を3件程度。短いタイトルと日付。「すべて」で一覧へ。
- 自分のやること：自分が担当する未完了タスク。期限超過 → 期限が早い順。日付と時刻を表示。
- 名前を選択していない「全員」タスクは、自分の所属グループの運営メンバーとして自分にも表示する。
- ホームに今日の配車、出欠人数、在庫警告、会計額、次の練習カード等を追加しない。
- 「自分」一覧に他人だけが担当する仕事を混ぜない。
- 0件時は各欄に短く「ありません」。ダミー件数や装飾イラストを出さない。

## 6. お知らせ

### 6.1 登録

入力欄は四つだけ：**タイトル、本文、対象、通知する／しない**。

投稿者は認証ユーザーから、投稿日時はサーバー時刻から自動記録。対象は幹部全員（運営メンバー全員）、担当単位、個人複数選択。初期値は全員。投稿内容はアプリ内にも保存。

### 6.2 閲覧・編集

一覧にタイトル・投稿日。詳細にタイトル・本文・投稿者・日時。既読人数、未読ドット、既読確認は設けない。編集時は作成日時を変えず更新日時を内部記録。通知は保存のたびに勝手に再送せず、「通知して更新」を明示選択したときだけ送る。削除は確認後、通知ジョブを取り消す。

### 6.3 通知

投稿保存成功後に対象の通知許可済み端末へWeb Push。送信に失敗しても投稿自体は残す。端末への到着や閲覧を保証したと表示しない。

## 7. 予定 — 既存アプリを母体にする

### 7.1 既存アプリに関する確認範囲

ユーザー申告：ChatGPT Siteに公開した予定アプリがあり、1日1件を基本とした登録と画像出力がある。本引き継ぎ時点ではその実装ファイル・正確な公開URLを特定できていない。旅行アプリを代替と見なして流用しない。

繰り返し、複数日選択、既存画像出力などの実装有無・挙動は、対象ソースを読んで一覧化する。実装されている機能を勝手に削らず、未確認の機能を「既存」と断言しない。

### 7.2 予定表は2種類

自由に予定表を増やす機能は今回不要。

- `club`：通常練習、大会、練習試合等の部活予定。
- `executive`：幹部会、打ち合わせ等の幹部予定。

画面上部の切り替えは **部活のみ｜幹部予定も表示**。後者では部活予定を消さず重ねて表示し、タスクの期限も幹部側の項目として表示する。

### 7.3 同日に複数件

部活予定も幹部予定も、一日に0～複数件を持てる。時刻が重なっても登録を禁止しない。同日の追加で既存予定を上書きしない。

日付を主キーにせず、すべての予定に不変の `event_id` を付ける。同日に午前練習と午後の練習試合があれば、出欠も配車も別の `event_id` に紐づく。

### 7.4 日時

日付必須。時刻なし予定を認める。時刻なしは「00:00」として表示しない。実装上、日付だけのデータと時刻付きデータを区別する。基準時間帯はグループのAsia/Tokyo。

幹部予定の開始・終了時刻は必要時だけ入力。終了が開始より前ならエラーとし、日跨ぎは終了日で表現する。複数日予定の参加単位は既存予定アプリに合わせ、配車に使用する実際の利用日は個別に記録できる。

### 7.5 部活予定詳細

日付、時刻、体育館、参加者名（学年別）を主に表示する。参加人数を大きなダッシュボードにしない。配車の登録済み、メニュー登録済み、関連タスク件数などの管理カードは置かない。

### 7.6 幹部予定の担当者

1人、任意人数、全員に対応。個人を選ばなければ**そのグループの運営メンバー全員**。フォーム表示は空欄ではなく「全員」と示し、未入力エラーにはしない。

内部では `assignee_mode='all'` と `assignee_ids=[]` を明示し、未読込やデータ欠落と区別する。全員の範囲は一般部員名簿全員ではない。

### 7.7 画像出力

部活予定だけの画像は既存出力を優先して維持する。幹部の個人名・仕事・通知条件を、部員向け部活画像に混入させない。

幹部予定込みの画面は複数行表示。月セルは一定件数で「＋N」を表示し、日付タップで全件を表示。画像書き出しでは「＋N」だけで予定を欠落させず、行高拡張か別紙一覧を使用する。画像書き出しの初期対象は部活のみ。変更が必要な場合も既存部活画像のデザインを不用意に変えない。

### 7.8 既存からの移行・更新

旧1日1件データは各日の値を長さ1の配列へ移し、安定IDを付ける。既存の名称・色・メモを失わない。移行は一度だけ実行し、再実行で重複させない。

予定の時刻・体育館変更で `event_id` を変えず、出欠と配車の関連を保つ。中止では未来の通知をキャンセルし、対応する配車を精算対象から外す。過去の精算確定済み履歴を物理削除しない。予定複製時には出欠の個別修正を丸ごと複製せず、参加の初期値を使う。

## 8. やること・幹部カレンダーの連携

### 8.1 タスク入力

タイトル、担当者、期限日、**期限時刻**、メモ、通知タイミング。状態は未完了／完了のみ。優先度、タグ、かんばん、細かな進行状態は不要。

補完判断：期限時刻は入力を省略しない。初期値23:59を表示して変更可能にする。担当選択は幹部予定と共通部品にし、1人を基本として複数・全員にも対応する。複数担当での完了方式は8.4に明示する。

### 8.2 一覧

**自分｜全体｜完了**。

- 自分：担当に自分を含む未完了のみ。期限順。
- 全体：未完了全部。担当者と期限日時を必ず表示。標準は期限順、担当者で絞り込み可能。担当者別の巨大なカード群を常設しない。
- 完了：完了済み。完了日時・完了者は詳細から確認。チェックを戻せる。

「担当者」と「この仕事の対象者」を別々の必須欄にしない。対象学年等が必要なら現段階ではタイトルかメモに書く。これは未確定要素を増やさないための補完判断である。

### 8.3 カレンダー表示

タスクを保存すると、同じ `task_id` の期限が幹部カレンダーに自動で現れる。別の予定レコードは作らない。

例：大会申込、担当山田、期限9/15 18:00 → カレンダーに「18:00 大会申込（締切）」が1件表示。タップでタスク詳細を開く。期限変更は一覧・ホーム・カレンダーに同時反映。タスク完了後は未完了期限の表示から外れ、完了一覧に残る。

幹部予定から必要なら「やることを追加」で準備タスクを作れる。`related_event_id` は任意で1件。これは予定とは別の仕事（幹部会資料作成等）の場合のみ。普通の練習詳細に関連タスク欄を常設しない。リンク元予定を中止してもタスクを勝手に完了・削除せず、編集時に関連を解除可能にする。

### 8.4 複数担当と完了

補完判断：複数担当タスクは**共同作業1件**として扱い、担当者の誰か1人が完了すると全体が完了。UIのチェックは1個。全員各自が行う必要のある作業は別タスクに分ける。個人別提出管理は初期版に増設しない。

幹部予定はタスクへ自動変換しない。担当付きの幹部会があるだけで「完了必須のタスク」を勝手に生成しない。予定はカレンダーで、作業はやることに載せる。ただし上記リンクで往復移動できる。

## 9. 通知・PWA

### 9.1 操作

予定とタスクで共通のチェック欄：**1か月前／1週間前／3日前／1日前**。複数選択可。全てOFFなら通知なし。初期値はグループ設定で1週間前＋1日前、個別に上書き可能。追加の通知ウィザードや複雑な条件式は作らない。

お知らせは投稿時のON/OFFだけ。細かな編集すべてを通知しない。

### 9.2 基準時刻（補完判断）

- タスク：期限日時から引く。
- 時刻あり予定：開始日時から引く。
- 時刻なし予定：対象日の09:00 JSTを基準に引く。予定表示は時刻なしのまま。
- 配車準備通知：対象の部活予定開始日時（時刻なしなら09:00）から引き、配車担当の運営メンバーに送る。一般部員名簿には通知端末がないので、全乗車者へ自動配信できると仮定しない。
- 「1か月前」は暦月で1か月前、同日がなければ月末へ丸める。30日前とは区別する。
- 作成時点ですでに過ぎている通知日時は遡ってまとめて送信しない。

### 9.3 二重通知防止

同じタスクがカレンダーにも表示されることを理由に二重配信しない。日時・担当の変更で古い未送信ジョブを無効化し、未来のジョブを再生成。完了・中止・退会・権限失効で不要なジョブを停止。送信直前にも対象者の所属と権限を確認する。

### 9.4 PWA実装条件

HTTPS、Web App Manifest、標準Web Push対応、通知購読保存、サーバー側の定期実行を用意する。従来型Web PushではService Workerを用いる。ホーム画面追加・通知許可の案内は設定または初回必要時だけ。

iOS/iPadOS 16.4以降のホーム画面WebアプリのWeb Push対応と、ユーザー操作による通知許可取得はApple/WebKit公式資料で確認済み。機能検出を行い、許可されていなくてもアプリ本体は利用可能にする。ブラウザを開いたままの `setTimeout` だけで期限通知を実装しない。到着時刻の完全保証はしない。

ローカルHTML試作には実際の認証・共有DB・Push送信はない。トーストを表示しただけで「Push実装済み」と報告しない。

## 10. 部員名簿

### 10.1 項目

**名前、学年、幹部上／幹部以下、大学配車／駅配車、メモ**。

氏名は必須。学年は1～6年を基本候補とし、必要なら「その他」。複雑な自動進級は作らない。個別に登録・編集する。インポート専用画面は初期版不要。

通常の参加初期値：幹部以下は参加、幹部上は不参加。例外だけ「通常の参加」を個別上書き可能にする。配車区分は運転者も乗車者も同じ属性を使い、名簿上で固定のドライバー役を強制しない。

### 10.2 メモ

一人ずつメモを持つ。運営上の短い注意等。配車表の共有画像には出さない。任意項目のため未入力時は一覧を広げない。

### 10.3 変更の影響

個人デフォルトや学年変更は、過去の出欠や登録済み配車を書き換えない。部員を非活動化しても履歴を残す。姓名変更は通常画面では新名を使い、精算確定済み出力の過去表示名はスナップショットを保持できるようにする。

## 11. 出欠

### 11.1 基本

参加／不参加だけ。遅刻・早退・保留・未回答はない。幹部が管理するため、回答依頼や全員への督促を作らない。初期出欠は名簿の区分と例外設定から作る。

### 11.2 二つの編集方向

**日程から｜部員から**。

日程から：部活予定を選ぶ → 学年別の名簿 → 名前行または参加状態をタップで切り替える。部員から：1人を選ぶ → その人の部活予定を日時順で並べる → 各日をタップで変更。

双方とも同じ `attendance(event_id, member_id)` を編集する。別々の出欠表を保持しない。学年全員を一括参加・不参加にする操作は作らない。

### 11.3 3か月分

現在日から暦上3か月後までにある部活予定の出欠をまとめて保持・表示する。すべてを最初の1画面で描画する必要はなく、月区切りにして読み込みを軽くする。

新しい部活予定、または期間内へ入った予定には不足分だけ初期値を追加。既存の手動変更を初期値で上書きしない。過去データは削除せず履歴保持。期間内に新入部員を追加した場合は追加日以降の対象予定だけ初期出欠を補完する。

### 11.4 配車との関係

参加へ変更した人は必要条件を満たせば未配車へ現れる。不参加へ変更した人が配車済みなら配車に差分警告を出し、ユーザーの確認で外す。登録済み配車や精算履歴を裏で無言に変更しない。

## 12. 体育館

体育館名、基本コート数、メモだけ。毎回入力せず登録済みから選ぶ。

当日の使用コート数が基本値と違う場合だけ予定側で上書き可能。体育館マスターを直しても過去の使用コート数は書き換えない。

**料金、料金表、面数×時間の費用計算、予約・支払状況の専用管理は初期版に入れない。** 料金を0円固定で表示することもしない。体育館名が未定なら「体育館未設定」と短く示し、未確認の場所を勝手に代入しない。

## 13. 配車 — 基本構造

### 13.1 入口・新規作成

運営 → 配車。最初は今後／履歴の一覧。右上「＋」で**部活予定を選択**する。幹部予定・タスク期限は候補に出さない。日付が同じでも時刻・体育館で区別し、対象 `event_id` を一つ選ぶ。

日付・体育館は選んだ予定から取得。毎回別フォームへ打ち直さない。予定があるだけで配車表を自動生成しない。

既にその予定の配車があるときは「開く」を標準にし、誤って同じ配車を複数作らない。大学配車・駅配車は一つの配車表内の区分。

### 13.2 表示する場所

行き先は体育館名だけ。出発地の住所・地点名を毎回入力させない。出発の分類は**大学配車／駅配車**で表現する。ドライバー・乗車者は名簿の分類を初期値として使うが、当日の移動先の区分を制限しない。

### 13.3 定員

**運転者を含め4人まで**。運転者1＋同乗者3。4/4などの数値は実データから算出。画像に4/4なのに3人しかいない等の不整合を再現しない。初期版に定員を毎回選ぶ欄を置かない。

## 14. 配車編集 — 最新UI

### 14.1 二列レイアウト

- 左：約2/3。大学配車／駅配車の区分見出しの下に車を縦に並べる。
- 右：約1/3。部員一覧を常時表示する。
- 左右の一覧は独立して縦スクロール。ページ全体の横スクロールは発生させない。
- 狭い画面でも右を隠して別ページにしない。氏名は表示名と省略補助で対応し、タップで全文確認できる。
- 画面上部：戻る、配車、登録。次の行に日付と体育館。小さい「コピー」「表」アクション。初期は往復同一。

### 14.2 右の部員一覧

その予定に参加している部員を基にする。

1. **配車必要**：原則、参加中の幹部以下。学年ごと。
2. **配車不要**：原則、参加中の幹部上。学年ごと。

ここでいう「不要」は選択・配置禁止ではない。幹部上も必要なら同乗者や運転者として配置できる。不参加者を「配車不要」に混ぜて乗車候補として表示しない。

すでに配置済みの人は右の未配置候補から外し、同一片道に重複乗車させない。配車必要の未配置人数は**赤い文字＋薄い赤背景または左線**で表示。配車不要の未配置者にはエラー表示しない。色だけに頼らず「未配車 N」の文字も持つ。

参加しているが自力移動する幹部以下は、その日・その片道だけ配車不要へ変更可能。名簿の幹部区分は変更しない。手動変更は小さなメニューから行い、全員の行に大きなスイッチを並べない。

### 14.3 車カード

見出しは運転者の名前（例：池田）と人数（例：4/4）。未指定なら「運転者」。

運転者欄は車の先頭の明確なドロップ先。その下が同乗者3枠。先頭へ落とした人だけが運転者になる。同乗者欄に最初に落とした人を勝手に運転者にしない。

「＋ 車」を押すと空のカードを作る。区分の「＋ 車」領域に人を直接落とすと、その人を運転者にした新車を作る。これにより初回ドライバー選択画面は不要。

### 14.4 ドラッグとタップ

右→左、車→別車、車→右、同じ車内の移動に対応。運転者も後から変更できる。

- マウスはドラッグ。
- タッチはハンドルから移動、または短い長押しで開始。通常の縦スクロールと競合させない。
- タップで人を選択 → 運転者欄／同乗者欄／新車領域をタップ、という代替操作を提供。
- キーボードでの選択・移動メニューも可能にする。
- 移動後に短い取り消し操作を提供。長い常設ヘルプは不要。

### 14.5 変更時の安全ルール

満員車への追加は元の位置へ戻して「4人まで」。運転者欄へ別の人を入れた場合、同乗者を維持し、前の運転者を右の候補へ戻す（補完判断）。無言で5人にしない。

他の車の運転者を移した場合、元の車は「運転者未設定」とし、同乗者を勝手に昇格させない。誰もいない車は削除可。人がいる車の削除は確認して全員を候補へ戻す。

一つの片道内で、同じ人が複数の車に乗ること・運転者兼同乗者になることを禁止する。車間移動は一つの原子的な更新とする。2人の配車担当が同時に編集した場合はバージョン競合を通知し、後勝ちで無言に上書きしない。

## 15. 配車コピー

### 15.1 操作

対象の部活予定を選んだ後、「コピー」から過去の配車を選択。直前だけでなく履歴から選べる。すでに編集中の配置を置き換える場合は1回確認する。

### 15.2 コピーするもの

大学／駅の区分、車の並び、運転者・同乗者の割当、行き帰りの構成。

### 15.3 コピーしないもの

コピー元の `event_id`、日付、体育館、出欠、通知の送信履歴、登録・実績状態、月次確定状態、過去の単価スナップショット、支払状態。

新しい配車は現在選んだ部活予定と現在の設定を使用する。コピー元は変更しない。

### 15.4 出欠の違い

新日程に参加する同一 `member_id` の人だけ割当を引き継ぐ。不参加・退部・別グループの人は除く。新しい参加者は未配車へ。旧ドライバー不参加なら車は運転者空欄のまま残し、同乗者を自動昇格させない。

差分は短く「不参加2人を除外」等で表示。コピーしただけで全員配車完了・登録済みにしない。コピー後も必要人数、重複、定員、運転者欠落を再計算する。

## 16. 往復・行き・帰り

### 16.1 通常

初期は**往復同じ**。一つの表を編集すれば両方へ反映。内部は行きと帰りを区別できる構造だが、通常の入力は一回で済む。

### 16.2 分離

「行き・帰りを分ける」で現在の配置を二つへコピーし、その後別々に編集。表示名は体育館名＋**（行き）／（帰り）**。往復表と片道表を同時に重複して精算しない。

全体が行きだけ／帰りだけの場合は不要な片道を無効にする。特定の人だけ片道不要の場合はその人の当該片道の配車必要設定を変更できる。

再び往復同じへ戻す際、二つが異なれば採用する方を選び、片方を上書きする旨を確認。両方を勝手に混ぜない。

### 16.3 回数

補完判断：**片道1回、往復2回**を初期ルールとする。ユーザーは回数×単価を希望しているが、「1回」の厳密な単位は会話だけでは完全には確定していないため、設定に「片道1回」を明示し、後から単価・例外回数を調整可能にする。

通常は乗車記録から回数自動取得。例外だけ回数・料金・対象外を詳細から修正。適用理由は内部に残す。自動の乗車事実と精算用の調整は別フィールドにし、料金調整で配車表の名前が消えないようにする。

## 17. 保存・登録・履歴

編集途中も下書き保存できる。配車必要未配置、運転者不在、定員超過があれば「登録」は進めず該当箇所を赤表示し、作業を失わないよう下書きは残す。

登録は配置を保存し、共有用配車表を作れる状態にする。日付が来たことだけを「実際に乗車したこと」の保証としない。履歴には登録した予定配車として保存し、違いがあれば担当が修正する。

コピーや保存は乗車事実を増やさない。1予定・1片道・1乗車者の有効乗車割当は一つ。日付・体育館・名前・単価は過去の月次確定後に勝手に変えない。

## 18. 最終配車表・画像共有

### 18.1 形式

ユーザーのExcel画像の簡潔な構造を採用。

```
9/12（土） 市民体育館（往復）
大学配車
┌────────┬────────┬────────┐
│ 池田   │ 中島   │ 山口   │ ← 運転者名を見出し
├────────┼────────┼────────┤
│ 井澤   │ 山田   │ 原塚   │
│ 小林   │ 江崎   │ 池谷   │
│ 杉山   │ 木村   │        │
└────────┴────────┴────────┘
```

運転者は見出しで一度だけ表示。同乗者は最大3行。**「1台目」「2台目」「池田車」の重複見出し、大きな車アイコン、全列の「運転」ラベル、余分な空行は不要。** 同姓の運転者だけ表示名を識別できる長さにする。

大学配車・駅配車は区分をまとめる。空の区分は出さない。行き帰りが異なるときはそれぞれ表を作る。編集用の必要／不要一覧、部員メモ、精算金額、下部タブは画像に含めない。

### 18.2 見やすさ

白背景、薄い罫線、見出しだけごく薄い緑またはグレー。Excelの元画像の青・ピンクに意味は持たせない。名前の表示領域を最優先し、小さなスマホ幅に全車を無理に縮小しない。

画面のプレビューは横スクロール可。書き出しは表そのものを自然な横幅で生成する。車が多いときは区分ごと、または一定列数ごとの段で全車を出力。画面で見えていない列も出力する。

### 18.3 共有

PNGを最低限の形式とする。対応環境ならOS共有、非対応なら画像保存。生成AIで文字を描かず、データからCanvas/SVG/HTML描画で生成する。人数・名前は保存データを唯一の正とする。ユーザーが押した時だけ共有し、一般公開URLを勝手に発行しない。

## 19. 月次配車精算

### 19.1 方法

**同乗した人から、その車を出した運転者へ直接支払う額**を計算する。部活が集めて再分配する設計にしない。運転者本人に自分自身の料金を課さない。

グループ設定に1回あたり料金を置く。実額は未設定とし、HTMLの300円等はサンプルだけ。単価未設定なら金額を捏造せず、回数のみ表示し「単価未設定」。

### 19.2 算式

乗車者A→運転者Bの月額 = 対象月の各乗車明細の `charge_count × unit_price_yen` の合計。

例：片道300円、同じ運転者の車に行きと帰りに乗る → A→Bは600円。同乗者3人なら運転者の受取は合計1,800円。異なる運転者に乗れば運転者ごとに別行。

双方向にお金が生じても、初期版で勝手な相殺・第三者への付け替え・支払回数最適化はしない。「誰に乗せてもらった分か」を残す。

### 19.3 集計対象

下書き・中止・未来の予定・精算対象外は除く。利用日を過ぎた登録済み配車から集計候補を作り、月次確定時に担当者が実際の利用と差分を確認する。日程経過だけで実乗車確認済みと表示しない。

料金設定変更が過去明細を再計算しないよう、乗車明細に単価のスナップショットを持つ。未来・未登録の配車だけ新単価が初期適用。既存配車の変更は明示的に行う。

### 19.4 画面

月を選ぶ → 「山田 → 池田 1,800円」等の一覧 → 行を開くと利用日・行き／帰り・回数・単価の内訳。運転者で絞り込めば受取内訳が分かる。

月次確定後の修正は再確定を明示し、履歴を残す。実際の送金・入金確認は初期版対象外。金額表示だけで「支払済み」にしない。

## 20. 練習メニュー — 機能を捨てずに統合

### 20.1 既存参照

現行の公開正本として `manatocookietwitter-lang/training-menu-app` の `main` を確認した。確認時HEADは `53d72586964a159682907196ce076bb517a47625`（2026-09-06 JST、`Unify home menu button colors`）。その直前の `b9466eb95e9f4a4fff5b7755d65ae95ca4e996cf`（`Refine training menu app UI flow`）を含む。`training_menu_app(8).html` は旧データ移行・回帰試験用の過去スナップショットとしてのみ保持する。

現行GitHubで確認した主な要素：4入口、3段階作成フロー、分類タブ＋種目選択、選択順、1〜5人中最大2人数パターン、人数別の人set/所要時間、`セットあり/1回のみ`、分・秒入力と画面内エラー、分類/メニューの通常編集＋編集モード、ドラッグ並び替え、削除Undo、画像保存時の履歴追加、画像履歴、portrait PWA。

### 20.2 統合方針

予定・出欠・体育館から日付、参加人数、利用面数、利用可能時間を渡す。これらは初期参照で、ユーザーが設定した人数パターン・セット数を勝手に再計算しない。出欠変更は明示的な反映操作にする。

計算は現行GitHubに合わせ、セット種目を人数パターンごとに `秒数 × set数 × 人数`、1回だけの種目を固定秒数1回として表示する。旧5人基準値は移行回帰用互換値に限定する。

UIは公開GitHubの最新版を優先し、部活運営アプリ固有機能だけを上乗せする。入口は縦4項目、緑白、角丸を抑え、選択中は淡緑＋左の選択順番号。作成は `1 メニュー / 2 セット / 3 出力`。実施方法は `セットあり / 1回のみ`。メニュー/分類は通常タップ編集、編集モードでドラッグ/削除。削除可能なマスターデータはUndoできる。画像出力はプレビューで `履歴にも追加する` を選び、`画像を保存` で保存＋履歴追加できる。履歴は小サムネイル一覧で、履歴画像削除は確認を挟む。

### 20.3 保存データ

グループごとの共有データへ移す際、既存ローカルデータは明示的な取り込み操作でコピー。元データを消さない。旧データ取込は再実行で二重登録しない。共有データの正は本番DBとし、古いローカルデータを勝手に全員へ同期しない。

## 21. 備品

備品名、現在数、単位、メモ。シャトルは例として「筒」。種類を分けたいときは別の備品項目として登録する。会話で未指定の銘柄を必須にしない。

数量は一覧から＋／−または直接入力で変更。0未満は禁止。最終更新者・日時を内部記録し、必要時に詳細から見られる。任意で不足判定のしきい値を設定し、下回れば備品画面内だけ赤で分かるようにする。

ホームへ在庫カードを追加しない。初期版では発注管理・消費履歴台帳・自動通知を作らない。通信失敗時は数量を元に戻し、変更失敗を短く示す。

## 22. 技術・データ保護

提案構成：既存実装との親和性を確認した上で、TypeScriptのフロントエンド＋共有DB＋認証＋サーバー側通知ジョブ。Supabaseは候補であり必須の契約済みサービスではない。外部サービスの作成・課金を勝手に行わない。

アプリ実行にLLM APIは不要。Luna等は開発に利用するだけ。静的HTMLだけで複数幹部への共有、認証、Pushが完成したことにしない。

本番では全テーブルでグループ境界と権限を検証。Supabaseを使う場合はRLSと最小権限を適用し、secret/service roleキーをブラウザへ埋め込まない。備考などの文字列はHTMLとして実行せずエスケープ。招待URL・Push購読秘密情報・個人メモを共有画像に含めない。

オフラインではキャッシュした情報の閲覧を基本とする。未送信編集はローカルの下書きとして分け、接続復帰時に最新版との競合を確認。画面から非表示にしただけの権限制御は禁止。

| D03 | タスクも複数・全員担当可、共同1件を誰かが完了 | 共通の担当選択を使い、複雑な個別提出管理を増やさない |
| D04 | 運転者差し替え時は元の運転者を候補へ戻す | 定員と責任者を勝手に変えないため |
| D05 | 未配車ありでも下書き可、登録時は不足解消が必要 | 作業を失わず、完成表としての誤共有を防ぐ |
| D06 | 月次は経過日の登録済み候補を担当が確認して確定 | 計画と実績の混同を防ぐ |
| D07 | 権限は担当ベースの標準テンプレート | ユーザーから設計を任されている範囲 |

| D09 | タスクの対象者独立フィールドは作らずメモで対応 | 未決の追加項目を必須化しない |
